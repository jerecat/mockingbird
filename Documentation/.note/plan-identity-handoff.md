## Current working direction (not implemented)

Replace the YAML top-level `name` with `plan`, for example:

```yaml
plan: basic-scenarios
sources:
  - name: design
    provider: git
    url: ...
```

Keep source `name` and Job `id` unchanged. The intended meaning is:

- `plan`: the continuing identity of the user's execution definition.
- `run_id`: one execution, generated by MB on every run.
- Re-running unchanged content and editing args/jobs can both remain the same
  named plan. Each run retains its actual configuration and expanded jobs.
- Use another plan name when the user intends another plan.
- `mb plan` validates/resolves the current commands and saves the execution
  plan. Do not add independent plan revision management.

This is a discussion direction, not an approved migration specification.
No runtime/YAML schema change has been made. Decide the scope of name uniqueness,
identity checks, rename/copy/move behaviour, and compatibility with existing YAML
and saved runs before implementation. Do not silently replace path validation
with unrestricted name matching.

## Last explanation given to the user

| Command | Role |
| --- | --- |
| `prepare` | Prepare MB's environment: acquire sources and save management information |
| `setup` | Execute optional user preparation commands, such as building simv |
| `plan` | Validate and resolve the commands/arguments to execute |
| `run` | Execute the saved plan and create a new run ID |
| `collect` | Collect and judge results through the collector contract |

In the standard command mode, no setup jobs means setup can be omitted.
Do not add before/after semantics to ordinary execution jobs: users can keep
build, sleep, simulation, and cleanup as an ordered job list if desired.

## Current implementation facts

- The top-level key is still `name`, a display name without global uniqueness.
- Definition identity is checked by the YAML's resolved absolute path.
- `workspace` holds `sources/<source-name>/` and `.reg/` management state.
- Different YAML definitions should use different workspaces. Prepare currently
  can overwrite another definition's management context in a shared workspace;
  subsequent use of the earlier definition encounters an identity error.
- `run_root` holds one directory per run; it is not the command cwd.
- Standard command cwd is the invocation directory saved by prepare. Relative
  command paths use that directory, not the YAML's directory or workspace.
- Separate YAMLs can share existing simv/scripts by using `sources: []`, separate
  workspaces, and commands referencing the same existing files. No re-clone or
  rebuild is implied. Setup process environment changes do not persist into run.
- Execution-only edits need plan then run, not prepare. Preparation changes still
  require prepare. Each run saves context, plan and per-job execution evidence.
- `.reg/last_run.json` is a pointer used by status/collect when run-dir is omitted.
  It is written before dispatch and again at execution completion, including
  failure/interruption. Concurrent runs in one workspace do not guarantee that
  it points to the latest-started run; the last writer wins.
- `.reg/last_result.json` points to the latest collected result, including pending
  results. Collecting an older explicit run can update it. It can differ from
  last_run. Previous run directories remain intact.
